# 量潮创始人工具箱（quanttide-founder-toolkit）

创始人工具箱——面向创始人角色的事务与工具集合。

## 解决什么问题

AI 读 Markdown 时只认语法（标题、列表、段落），不认语义——不知道「这段是档案」「这条是洞察」。用正则硬写提取逻辑，换个写法就崩。

而 memory 和 fiction 这两个仓库有一个共同点：**都是靠目录命名约定组织的 Markdown 文档集合**——目录名和文件名承载结构含义（`journal/ profile/ insight/ roadmap/`、`{序号}_{标题}.md`），正文只管内容。这意味着「怎么读」可以写成规则，不用靠正则猜。

## 怎么做

分三步：

| 步骤 | 做什么 | 怎么做 |
|---|---|---|
| 一、语法解析 | 识别 Markdown 的标题、段落、列表、分隔线 | 正则，只管结构 |
| 二、结构切分 | 按标题层级切出章节 | 正则，只管结构 |
| 三、语义提取 | 从章节里提取业务字段 | 规则文件 + LLM |

前两步通用，任何 Markdown 文档都一样。第三步靠规则文件描述每种文档怎么读，LLM 按规则提取字段。

规则是数据不是代码——改写法只改规则文件，不改引擎。LLM 按规则提取，不自由发挥。

## 规则文件

规则文件描述一种文档类型怎么读：标题从哪来、说明在哪、章节怎么切、提取哪些字段。以 profile 为例：

- 标题取第一个 H1，兜底用文件名
- 说明是 H1 与首个 H2 之间的段落
- 按 H2 切节、H3 切子节
- 提取 name / paragraphs / items 三个字段
- 未知内容保留在 paragraphs，不丢弃

每种文档类型一份规则，后续扩展 insight、roadmap。

## 两个仓库的共同结构

memory 和 fiction 用的是同一套组织方式：

| 共同点 | memory | fiction |
|---|---|---|
| 结构靠目录命名约定 | `journal/ profile/ insight/ roadmap/` | `{N}_{阶段}/` 前缀 |
| 文件命名承载元数据 | `YYYY-MM-DD.md` 文件名即日期 | `{序号}_{标题}.md` 文件名即编号 |
| 从原始到精炼 | journal（原始）→ insight（提炼） | 观察站（原始）→ 灵感→场景→初稿→定稿 |
| 找特征目录发现内容 | 含 `journal/profile/insight/roadmap` 任一子目录 | 含 `index.md` 或 `N_` 阶段子目录 |
| 允许结构缺失 | 无假说节、无元目标、无一级标题均可解析 | 未编号章节、预留空号、无 index.md 均可处理 |

因为结构相同，两个仓库共用同一套解析代码，只换规则文件。

## 提取器

- **规则提取**：纯规则匹配，无 LLM 时的降级方案
- **LLM 提取**：按规则提取，首选方案
