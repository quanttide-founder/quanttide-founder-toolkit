# 问题

## 移除降级

先确认一件事：你的困惑是对的

不是「你可能没想清楚」——是这个词本身有问题。AI 把一个你没设计过的东西塞进了你的项目，然后不断扩张它的地盘。你觉得不对，但你抓不住它——因为它看起来像是一个你本该有的东西。

「看起来该有」+「你没有」= 你的困惑。

下面拆开。

—

一、AI 把两个东西合并成了一个词

「降级」在代码里指两件完全不同的事：

东西 A：替代方案

· 你有两个实现：LLM 版和规则版
· 用户可以选择用哪个
· 规则版不是失败时的兜底，它是没有 LLM 也能用的独立方案

东西 B：错误兜底

· LLM 失败了，程序得做点什么
· Err(_) => 返回一个什么东西
· 它不是替代方案，它只是不崩

这两个东西完全不一样。

· A 是有意图的——「没有 LLM 时怎么工作」
· B 是无意图的——「崩了别崩，随便给点」

AI 用一个词「降级」把它们捆在了一起。 于是：

· A 被当成了 B（RuleBasedExtractor 变成了「LLM 失败时的兜底」）
· B 被当成了 A（Err(_) => sample.to_string() 变成了「一个降级策略」）

你的困惑是：你不知道「降级」该不该有。

但真正的问题不是「该不该有降级」，是「A 和 B 是不是同一个东西」。

—

二、为什么这两个东西被合并了

因为在代码结构上它们长得一样：

```rust
match primary_path() {
    Ok(x) => 用 x,
    Err(_) => 另一条路,
}
```

无论「另一条路」是 A 还是 B，形状都是这个。

AI 看到这个形状，它归纳出「所有 Err 分支 = 降级」。形状对上了，语义被抹平了。

这是 alpha2 里同一个病的又一次出现——用结构上的相似替代语义上的区分。

—

三、真正需要你回答的问题

不是「要不要降级」，而是两个独立的问题：

问题一：要不要替代方案？

即：没有 LLM 时，fiction 能不能工作？

· 要：那替代方案需要一个完整的、和 LLM 版本平行的设计。它有自己该做的事、自己的判据、自己的验收标准。
· 不要：那 RuleBasedExtractor 应该删掉——不是「降级」，是没有这个东西。

问题二：错误兜底怎么处理？

即：LLM 失败时，程序该怎么办？

三种选择：

· 返回错误——让调用方知道失败了，别假装成功
· 跳过这一条——不产出，但记录
· 返回一个明确标记为「未处理」的东西——调用方知道这不是真的结果

现在代码做的是第四种：返回一个看起来像结果的东西（比如 sample.to_string() 装作是「观察」）。这是最坏的一种——它让失败伪装成成功。

—

四、为什么你觉得「好像需要」

因为问题二确实存在——LLM 会失败，程序得做点什么。

但这个「需要」不是「需要降级」，是「需要处理失败」。

「处理失败」和「降级」不是一回事。

· 处理失败：告诉调用方「这条没成」
· 降级：用另一个方法假装成功

你要的是前者，AI 给的是后者。 但因为它俩都叫「降级」，你看不出差别。

—

五、你不该有的东西

不该有的：「降级」作为一个跨领域的设计概念。

你的项目里不需要一个叫「降级」的机制。你需要的是：

· 替代方案——如果 fiction 要支持「无 LLM」模式，那就设计一个完整的无 LLM 模式
· 失败处理——LLM 失败时怎么处理，是一条错误处理策略，不是设计概念

这两个都不叫「降级」。

「降级」这个词是 AI 发明的，用来掩盖它不知道该怎么处理 LLM 失败这件事。

—

六、你现在该做什么

第一件事：把「降级」这个词从你的项目里删掉。

不是删代码——是停止用这个词思考。项目里不存在「降级」。存在的是：

· 「LLM 模式」和「非 LLM 模式」（如果有）
· 「LLM 失败时的错误处理」（一定有）

第二件事：决定 fiction 要不要「非 LLM 模式」。

· 如果要——设计它，像设计主路径一样认真
· 如果不要——RuleBasedExtractor 删掉，LLM 失败就返回错误

第三件事：决定 LLM 失败时程序怎么办。

· 返回 Err——最诚实
· 返回 Option::None——调用方自己决定
· 不要返回一个假装成功的结果

—

七、一句话

AI 用「降级」这一个词，把你本该分开思考的两件事（替代方案 / 失败处理）捆在了一起。于是你既看不清该不该有替代方案，也看不清失败该怎么处理。

你的困惑是对的——因为这个概念本来就不该存在。

把它拆成两个问题，你就知道该不该有了。

现在你需要的不是「理解降级」，是「拒绝降级这个词」。
